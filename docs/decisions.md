| D1 | 2026-11-15 | **Separate repository** (`AteAnne`), not inside the portfolio repo | Spec: never merge with Kulayan, the commute guide or the portfolio. |
| D2 | 2026-11-15 | **Mobile-first installable PWA**: manifest, iOS meta, safe-area insets, service worker caching only the public shell | Owner asked for "download as an app on iPhone and Android, optimised for iPhone". | D4 | 2026-11-15 | **OOP layering**: immutable value objects, domain service classes, aggregate root, abstract `BaseService`, storage interface, DI container | Owner asked for OOP. Pure domain classes stay framework-free and exhaustively testable. |
| D5 | 2026-11-15 | Money = `bigint` centavos everywhere; `Fraction` for exact weights; JSON uses decimal strings | Spec: no floats; avoid JS number precision issues. |
| D6 | 2026-11-15 | **Stable participant order = join sequence (`Member.seq`)** for tie-breaking and netting | Deterministic, human-meaningful, survives renames and recovery; cuid order is not guaranteed. |
| D7 | 2026-11-15 | **Lock the event row** for every money write | One simple, consistent lock order. Group sizes (≤20) make contention negligible; prevents over-claim and over-report races. |
| D8 | 2026-11-15 | Join codes stored as HMAC + **AES-GCM ciphertext** so the owner can re-display a valid code | Hash-only would force a rotation every time the owner forgets the code. The key is derived from `JOIN_CODE_HASH_KEY`. |
| D9 | 2026-11-15 | Shared join links put the code in the **URL fragment** and clear it after reading | Fragments are not sent to servers or logs. |
| D10 | 2026-11-15 | Receipt edits are only allowed in Collecting; owner corrections are audited `receipt.organizer_correction` and make claims stale | Simplest faithful reading of "visible proposals, no silent edits": people re-confirm their own claims. | D11 | 2026-11-15 | Claims saved per receipt with `finish` / `none` / `draft` | Distinguishes genuine zero (`none`) from unanswered, while allowing saved progress. |
| D12 | 2026-11-15 | A rejection automatically opens a dispute; it resolves only when **both** pick the same answer; "re-record" allows exactly one linked replacement report | Spec's versioned two-party resolution, without asking the sender to pay again. |

| D15 | 2026-11-15 | Whole-event deletion is blocked once any payment is reported | The spec requires all members to approve deletion after reports; that flow is deferred, so v1 blocks it and offers export. |
| D16 | 2026-11-15 | Member removal only while Collecting and only if unreferenced | Prevents erasing ledger references. Deactivation of referenced members is deferred (gap noted in requirements). |
| D17 | 2026-11-15 | Live updates by polling every 15 s plus on focus, not websockets | Simple, works on serverless or edge hosts and in installed PWAs. |
| D18 | 2026-11-15 | Read model fetched client-side; page shells contain no private data | The service worker may cache shells safely; private JSON is always `no-store`. |
| D19 | 2026-11-15 | Accept JPEG/PNG/WebP. The file input uses `accept="image/jpeg,image/png,image/webp"` | iOS Safari then converts HEIC photos to JPEG on upload. |
| D21 | 2026-11-15 | Example names changed to generic **Mark, Juan, Paolo** (and neutral seed names); scenario text removed from the home page | Owner request. | D22 | 2026-11-15 | **First-visit ask + 12-step tutorial**: a bottom-sheet "First time here?" on first visit (any page), and a "?" / "Tutorial" button on Home, the event header and People | Owner request. | D23 | 2026-11-15 | **Vercel-ready**: images stored in PostgreSQL (`AssetBlob`, `STORAGE_DRIVER=database` default; `disk` for self-hosting); phones shrink photos before upload (Vercel 4.5 MB body limit); `vercel.json` with the `sin1` region and a daily cron; `vercel-build` migrates only production deployments | Vercel functions have no persistent disk. Keeping images in the database avoids a second storage service, stays private behind the authorized route, and one database backup covers money and images. Fine at small-group volume. |
| D24 | 2026-11-15 | **All events auto-delete 30 days after creation, finished or not** (`RetentionPolicy`, `EVENT_RETENTION_DAYS`) | Owner decision. It overrides the spec's baseline (180 days for Done; never auto-purge unresolved events). Mitigations: the deletion date is shown on every event, there is a 7-day warning, export is one tap, and the create page states it. The purge runs in the app (ordered delete plus image bytes), because a raw SQL delete is blocked by the ledger's restrict FKs. |
| D25 | 2026-11-15 | Migration enables **RLS with no policies on all tables** and revokes Supabase `anon`/`authenticated` | Supabase exposes `public` over its Data API; AteAnne uses only its own server routes. Owner-role connections bypass RLS, so the app is unaffected. No-op on plain Postgres. |
| D26 | 2026-11-16 | **Preview mode**: a deployment without database settings builds and serves the UI; APIs return 503 `not_configured`; a banner explains it | The owner wanted to explore the deployed UI while setting up Supabase. Fails safe: nothing can be written without a database. |
| D27 | 2026-11-16 | **Receipt scanning with Claude vision** (photo → *draft* only) | Owner request; overrides the spec's v1 "no AI/OCR". Guardrails that keep the spec's intent: the draft is never saved automatically and opens in the normal editor, where the person must check it and the reconciliation must pass; a pure `ReceiptDraftNormalizer` parses amounts exactly, drops malformed values with warnings, and converts VAT-exclusive discounts to the VAT-inclusive equivalent only when a 12% gross-up explains the gap (the pictured-receipt fixture, 592.63 → 663.75). Photos are re-encoded (metadata stripped) and resized before sending; the prompt tells the model not to copy names, card or loyalty numbers. Optional (needs `ANTHROPIC_API_KEY`); rate-limited per person (10/h) and per event (40/day) because each scan is a paid call. Model `claude-opus-5-5` at effort `medium`, with server-side refusal fallback. **Privacy:** scanned photos are sent to Anthropic's API for processing. |
| D29 | 2026-11-16 | Groq reader uses **JSON mode, not `json_schema`**; default model **`qwen/qwen3.8-27b`**; no SDK retries; prompt records subtracted VAT (senior/PWD "VAT exemption") as a discount | Live testing with the owner's key: `json_schema` with images returned garbage values, `qwen/qwen3.6-27b` isn't offered, the free tier is 7,000 input tokens/min (retries would hang the request), and senior receipts subtract VAT before the 20% discount. Results are in test-report.md. |
| D28 | 2026-11-16 | **Groq as the default scanner** (`GroqReceiptReader`, free tier) behind the same `ReceiptReader` port; Claude stays optional; `RECEIPT_SCAN_PROVIDER` picks when both are set | Owner wants no paid API. Groq's free tier covers small-group volume. Asks for `json_schema`, falls back to JSON mode, strips reasoning text, validates with the shared Zod schema; same normalizer and review-before-save flow. No separate server (Render) needed: the Vercel route calls Groq directly. The model ID is configurable because Groq's vision lineup changes (default was a Preview model). |
| D20 | 2026-11-15 | `entryComplete` flags are not reset by receipt edits | Receipt changes already invalidate funding acks, claims and approvals through versions; resetting entry flags would add friction without protecting money. |
| D30 | 2026-11-16 | **Scan block always has two plain buttons ("Take photo" / "Upload photo")**, a visible reading state with Cancel, and errors that stay on screen; when no reader is configured the organizer sees a small "Photo scanning is off on this site · Why?" note instead of nothing | Owner could not tell why the scan option was missing in production. | D31 | 2026-11-16 | **Forgiving optional settings** (`readEnv` in `config.ts`): blank optional values count as unset, pasted quotes/spaces are stripped, and mistyped names for the Groq key (`groq_api_key`, `GROQ_KEY`, …) are accepted | Dashboard typos were the most likely reason scanning stayed off, and a blank optional box previously put the whole site in preview mode. | D32 | 2026-11-16 | **Feedback on every tap**: all buttons dip when pressed; `Button` shows a spinner and blocks double taps while its action runs, then a tick; a thin activity bar shows during any save; toasts moved to the browser **top layer** (popover) at the top of the screen | Owner asked for clear button feedback. | D33 | 2026-11-16 | **One button system in `globals.css`** (`.btn` + `-primary / -secondary / -tonal / -ghost / -danger / -receive / -add`, `.icon-btn`, `.segmented`, `.stepper-btn`), used by the `Button` component and by plain buttons (tutorial, install tip) | Owner asked to focus on button design. | D34 | 2026-11-16 | **Reader copies, a separate layer checks.** The reader now also returns unit prices and the printed items subtotal ("Gross Sales") and is told never to calculate. `ReceiptDraftNormalizer` cross-checks quantity × unit price = line total and lines = printed subtotal (believed only when it agrees with the printed total), and corrects a value only when exactly one explanation fits: a line total that should be quantity × unit price, or one look-alike digit (5/6, 3/8, 1/7, 0/8…) in an item or the service charge. | D35 | 2026-11-16 | **VAT-exclusive discount conversion is exact** (printed × 1.12, ± 2 centavos), replacing the old "up to 13.5%" window | On the owner's receipt the loose window "reconciled" a wrong reading by inflating the discount to 633.75, hiding two misread amounts. |
| D36 | 2026-11-16 | **The reader's copy of the photo is cropped to the paper** (`src/server/scan/receiptImage.ts`) when a clear bright strip is found; phones now upload receipts at up to 2600px (was 2000). | D37 | 2026-11-18 | **Guests: people without a phone.** A guest is an ordinary member with `managed = true` and no browser. The organizer or an admin *acts for* them: the app sends `x-ateanne-act-as: <memberId>`, and only routes for a participant's own actions accept it (`ctx.caller()`: claims, funding, entry, approval, receipts, photos, payment reports/decisions, disputes, cash/QR details). Every other route uses `ctx.actor()`, which **refuses** the header, so nothing is ever done "as" someone by accident. `GuestPolicy` (pure, `src/domain/event`) decides who may act for whom; `BaseService.inEvent` resolves `me` (the guest) and `by` (the real person) inside the event lock, and every audit entry made while acting records `by` as the actor and the guest as `onBehalfOf`. | Owner's pilot with cousins: some relatives have no phone/data or aren't comfortable with apps. Reusing the normal screens (the view is built *as* the guest) means guests get every rule the app already enforces, with no second code path for money. |
| D38 | 2026-11-18 | **Admins** (`Member.isAdmin`) are appointed by the organizer and can only add guests, act for them, remove unreferenced guests and hand them their own access. Limiting admins to guest care keeps the organizer's powers in one person while letting a second relative help. |
| D39 | 2026-11-18 | **No conflict of interest when acting.** A manager acting for a guest cannot confirm a payment *they themselves sent* to that guest, or answer a dispute where they are the other side. | D40 | 2026-11-18 | Guests are added only while Collecting (same rule as joining), start with entry marked complete (the payer confirmation still gates anything they paid), and can **take over with their own phone**: a manager makes a one-time key, the guest redeems it like a recovery key, and `managed` becomes false.
